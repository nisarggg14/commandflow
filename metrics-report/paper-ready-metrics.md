# Paper-ready metrics

CommandFlow was evaluated through a reproducible source and runtime audit of revision `a3ae2a7` on branch `feature/mcp-runtime`. The implementation contains 33 registered MCP tools, organized into seven categories, and exposes 21 Next.js API routes. The persistence layer defines 12 Prisma models and seven migration directories. The application source inventory contains 112 TypeScript/JavaScript-family files and 7,193 physical lines, including 6,243 nonblank lines; these counts describe implementation size only and are not used as quality or security proxies.

Runtime tool metadata identified 20 effective LOW-risk tools, seven MEDIUM-risk tools, and six HIGH-risk tools. Twenty-five tools declare risk explicitly, while eight rely on the registry's LOW-risk default. All six HIGH-risk tools declare step-up MFA, and the MCP server contains a separate approval path for HIGH-risk execution. These figures are source/runtime metadata measurements; the automated runtime tests could not execute in the audit environment.

The repository contains six test files and 63 test declarations. The configured test runner discovered all six files but failed before executing test bodies because Windows returned `spawn EPERM`. Consequently, no pass rate or coverage percentage is reported. TypeScript typechecking completed successfully. ESLint was unavailable because the configured executable was not installed, and the production build was incomplete after prolonged compilation without a terminal result.

Warm local microbenchmarks measured 10,000 sequential Zod schema validations and 10,000 MCP authorization checks. Median times were 0.9 microseconds and 0.5 microseconds, respectively; p95 values were 2.0 microseconds and 0.9 microseconds. These values measure local control operations only and exclude database, network, and model inference latency. An end-to-end mock client measurement was not reported because the existing SSRF control rejected the loopback target; no external API calls were made. LLM latency was not measured because the required provider key was unavailable and no paid provider calls were attempted.

The results establish a reproducible implementation baseline, not a production performance, availability, penetration-testing, or formal-verification claim. Hardware inventory was unavailable because WMI access was denied, and the limitations should be retained when presenting these measurements.
